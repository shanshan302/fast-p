# Fast-P 需求与架构

## 目标

Fast-P 是一个面向 Windows 的轻量桌面比价截图工具。用户选择 Excel、平台和输出目录后即可执行长批次任务；程序不依赖 Agent、Skill 或用户手动运行 Python/Node 命令。

最终交付为 Windows 安装程序，内置 Python/Tk、Node、fast-cli、Playwright、Chromium 和运行依赖。平台登录状态保存在用户目录，程序升级不覆盖登录数据和任务数据。

## 业务流程

输入表格至少包含型号、标准厂牌、供货价和最小起订量，敦煌 SKU 可选。

每个型号按用户选择的平台优先级串行采集。候选商品同时满足以下条件时命中并停止后续平台：

- 型号匹配；
- 厂牌或厂牌别名匹配；
- 平台数量不小于最小起订量；
- 平台价格高于供货价；
- 存在有效商品链接。

每个型号最多保留一个平台结果和一张截图。单项失败不终止整个任务，进度逐项保存，可取消、恢复和重试。

## 能力边界

| 能力 | 输入 | 输出 | 不负责 |
| --- | --- | --- | --- |
| 采集 | 型号、平台、厂牌提示、MOQ | 标准化候选商品 | 截图、Excel、最终比价结论 |
| 比价规则 | 候选商品、供货价、MOQ、标准厂牌 | 命中结果或未命中原因 | 浏览器和平台采集 |
| 截图 | URL、文件名、截图配置 | 图片或明确错误 | 平台采集和比价规则 |
| 任务编排 | Excel、平台顺序、任务状态 | 采集和截图队列 | 平台内部实现 |
| 导出 | 任务结果和截图路径 | Excel、报告和 ZIP | 采集和截图 |

采集和截图是可以单独调用的能力。完整任务只由编排器组合这些能力：

```text
Excel -> 采集 -> 比价判断 -> 保存结果
                              |
                              v
                         独立截图队列
                              |
                              v
                            导出
```

界面提供“只采集”“只截图”“采集并截图”三个入口。截图能力读取包含“商品链接”列的 Excel，只认识 URL，不依赖 fast-cli、平台策略或厂牌规则。

## 轻量原则

- 使用 Tkinter 桌面界面，不引入 Electron；
- 使用 SQLite 保存任务状态，不引入外部数据库；
- 同时只运行一个采集 Worker 和一个 Chromium；
- 不引入 Web 服务、Redis、消息队列、进程池和常驻看门狗；
- 采集、截图、规则和导出通过小型版本化数据结构交互；
- Chromium 是安装体积的主要部分，其他部分保持最小依赖。

## fast-cli 评估

现有 fast-cli 的平台策略、配置、搜索 URL、结果标准化和测试可以继续复用，但一次性 CLI 进程模型不适合作为长批次执行引擎。

已确认的风险：

1. 每次型号/平台查询都会重新启动 Node、加载 Playwright 和策略；
2. 带厂牌查询会重建厂牌索引，本机实测单进程峰值约 142MB、初始化约 1.9 秒；
3. 多平台默认并发，Chrome 内存压力会随平台数上升；
4. 默认 JSONL 会把大量商品明细送入 Agent 上下文；
5. Chrome 由短命 CLI 以 detached 方式保留，没有唯一任务所有者；
6. 并行 CLI 可能争用同一 Profile、CDP 状态和页面；
7. `--close-tabs` 只能缓解标签页积累，不能解决进程、内存和所有权问题；
8. 当前测试覆盖单次行为，没有长批次压力测试和中断恢复测试。

因此保留平台策略，重写外层批量运行方式。

## 持久采集 Worker

Fast-P 启动一个 Node Worker。Worker 在整个采集阶段拥有浏览器/CDP，按 JSONL 协议串行处理请求：

```json
{
  "apiVersion": 1,
  "id": "row-20-hqchip",
  "action": "collect",
  "partNumber": "BAV99",
  "platform": "hqchip",
  "brand": "PANJIT/强茂",
  "brandVariants": ["PANJIT", "强茂"],
  "minBuyQty": 100
}
```

Worker 的约束：

- 同时只处理一个请求；
- Node、策略和厂牌资源只初始化一次；
- 每次请求使用独立页面，请求结束关闭页面；
- 输出紧凑结果，不把明细写入 Agent；
- Worker 退出时关闭自己管理的浏览器；
- Worker 异常退出时由 Fast-P 重启，并从 SQLite 重试当前项；
- 不使用独立看门狗；父进程只处理自己启动的 Worker 生命周期；
- 根据 Windows 压力测试结果决定是否按固定批次主动回收 Worker/浏览器。

## 截图能力

截图引擎接收 URL 和输出文件名，使用专用 Profile 打开真实商品页，隐藏遮罩后截图，并保留 URL 证据栏。截图错误写入任务结果，不影响其他项。

采集和截图不同时占用同一个 Profile。编排器在采集阶段结束并释放采集浏览器后，再启动截图阶段。独立截图任务可以直接读取含 URL 的结果文件。

## fast-cli 更新包

安装包内置一个经过验证的 fast-cli 基线版本。高频更新使用独立运行包，不复用仅包含 Agent 文档的 `fast-cli-skill.zip`：

```text
fast-cli-runtime-win-x64-0.1.8.zip
├── manifest.json
└── fast-cli/
    ├── package.json
    ├── bin/
    ├── src/
    ├── config/
    ├── strategies/
    └── node_modules/
```

导入更新包时校验包名、版本、平台、Node 要求、协议版本和解压路径；解压到版本目录后运行 `--help`、`platforms` 和 Worker 握手检查。全部通过后原子切换，失败继续使用旧版本，并保留上一个版本用于回退。

fast-cli ZIP 只能替换采集能力，不修改截图、比价规则、SQLite、导出和界面。
Fast-P 通过 fast-cli 的 `platforms` 命令读取启用平台，因此运行包新增或停用平台后不需要修改 Fast-P 代码。

```text
任务结果/

```

## 诊断

应用日志写入用户目录并自动轮转。诊断包由用户主动导出，只包含脱敏日志、应用/Python/Node/Chrome/fast-cli 版本、任务状态计数和最后进度事件；不复制浏览器 Profile、Cookie、密码或原始 Excel。

Mac 开发环境使用独立 Python 3.12 虚拟环境。Windows 安装包由后续的 Windows CI 构建，不在 Mac 上交叉编译。

## 验收重点

- 采集、截图可以分别运行；
- 采集策略更新不影响截图和导出；
- Worker 异常退出后可以恢复当前任务；
- Windows 环境连续执行数百个真实型号，不出现页面和进程持续增长；
- 页面超时后下一项仍可正常执行；
- 任务中断后已完成结果不重复采集；
- fast-cli 更新失败可自动使用旧版本。
